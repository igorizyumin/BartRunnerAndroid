# BART GTFS and GTFS-Realtime normalization guide

## Purpose

This guide translates the empirical fixture audit into implementation rules for
developers building BART schedule, realtime, ETD, and route-planning layers. It
describes where normalization belongs, which source owns each fact, and where
the implementation must preserve uncertainty instead of manufacturing a
clean-looking answer.

The evidence is generated under [`docs/bart_data_audit`](C:/Users/Igor/StudioProjects/BartRunnerAndroid/docs/bart_data_audit/). The normalization analysis uses the checked-in GTFS ZIPs, GTFS-Realtime protobufs, and ETD XML boards. Official Yellow-line PDFs are retained only as optional regression fixtures.

## Executive rules

1. Use static GTFS for published trip shape: station order, line, direction,
   scheduled times, and published terminal.
2. Use GTFS-Realtime for timing and explicit status changes when its `trip_id`
   maps to static GTFS.
3. Treat a GTFS-Realtime stop list as an observation, not necessarily a full
   trip pattern. The captured feeds had partial stop lists in 408 of 483 trip
   updates, and stop sequences were absent from the normalized stop rows.
4. Never treat an absent realtime entity as a proven cancellation. In these
   snapshots, omission is not distinguishable from feed timing, partial-feed,
   or capture-window behavior without later labeled evidence.
5. Keep 600–799 records in a separate operational-telemetry layer. They have
   no stable passenger-trip identity in the captures: all 68 numeric records
   lacked a route ID and none mapped directly to static trips.
   A DMU observation nevertheless implies a required electric counterpart:
   passengers must transfer north of Pittsburg/Bay Point (PITT), so DMU service
   cannot physically operate as an independent passenger service.
6. Use ETD only as corroborating passenger-facing evidence. ETD is rounded to
   whole minutes, has a limited look-ahead, can say `Leaving`, and exposes no
   GTFS trip ID.
7. Keep the official schedule PDFs only as optional regression fixtures for
   special cases, especially late-night Yellow service to Millbrae. They are
   not runtime inputs or a schedule source of truth.

BART has confirmed an additional source-system boundary: trip IDs generated by
the BART-to-Antioch system are not coordinated with trip IDs generated by the
BART schedule system. In particular, GTFS-Realtime trip IDs in the 600 range
for Pittsburg Center and Antioch have no GTFS match by design. This is not an
unknown-data anomaly and must not be “fixed” by guessing a static trip join.
The accompanying service alerts are not machine-readable in the normalization
context covered by this guide, so they cannot resolve the identity gap.

## Recommended normalization pipeline

```text
raw capture
  -> provenance and time normalization
  -> static GTFS catalog
  -> realtime entity/stop observations
  -> exact static/realtime association
  -> conservative semantic corrections
  -> optional ETD corroboration
  -> consumer-specific projections
```

Each stage should retain its input identifiers and confidence. A later stage
may add an interpretation, but should not overwrite the raw fact.

## Stage 1: provenance and time normalization

Create a capture record before parsing service data.

Minimum fields:

```text
capture_id
capture_directory or source_path
local_capture_timestamp
gtfsrt_feed_timestamp
etd_request_timestamp(s)
static_feed_version
component_sha256 (one hash per raw input component)
component_presence
capture_flags
```

Rules:

- Parse capture-directory timestamps in `America/Los_Angeles`.
- Store event timestamps as UTC instants plus the original local/service-date
  context.
- Keep `service_date` separate from the event's calendar date. A scheduled
  `24:15:00` belongs to the service date and is 00:15 on the following civil
  day for instant calculations.
- Compare ETD request time with GTFS-RT feed time. The checked-in complete
  captures were generally only a few seconds apart, but the difference must be
  recorded rather than assumed to be zero.
- Flag missing GTFS-RT, missing ETD, incomplete station sets, known disruption
  captures, and large cross-source time differences. Alert files may be
  inventoried as raw capture context, but are not normalization inputs here.
  Do not silently drop flagged captures.

The capture manifest is the right place to decide whether a comparison is
strictly suitable. It is not the place to discard the evidence.

The audit hashes each `trip_updates.pb`, `alerts.pb`, and ETD XML file in
`capture_components.csv`. Static ZIP hashes and per-table hashes are in
`static_sources.json`; `capture_sha256` is a deterministic digest of the
sorted component inventory for one capture.

## Stage 2: static GTFS catalog

### Service-date activation

Implement service activation as:

```text
calendar.txt range and weekday
  then calendar_dates.txt exception override
```

Keep the selected `service_id` on every normalized trip. Do not infer a
service date from a trip ID. The feed's `feed_info` dates are useful metadata,
but the calendar rows are the schedule-availability authority for a requested
date.

When more than one static ZIP is available, parse and compare all of them
before selecting one. Select the feed with maximum active-trip coverage for
the observed service dates, then use feed version and path as deterministic
tie-breakers. If table content is identical, record that fact but retain every
source hash and path.

### Time representation

Keep both:

```text
raw_time = "24:15:00"
seconds_after_service_midnight = 87300
absolute_time = service_date at local midnight + 87300 seconds
```

Never normalize `24:xx:xx` to a same-day `00:xx:xx` string. That creates false
ordering and wrong-day bugs in late-night routing.

### Station and platform normalization

For every stop-time row retain:

```text
raw_stop_id       # e.g. W40-3
parent_station    # e.g. MLBR
platform_code     # e.g. 3
stop_sequence
arrival_time
departure_time
```

Use `parent_station` as the passenger-station identity. Use the suffix/platform
only for platform-sensitive matching and diagnostics. Never discard the raw
platform stop ID because it can explain why two otherwise similar observations
are different.

### Route and line catalog

Build a route mapping from `routes.txt`, preserving the raw route ID and
direction suffix:

```text
1  -> Yellow-S
2  -> Yellow-N
3/4 -> Orange
5/6 -> Green
7/8 -> Red
11/12 -> Blue
19/20 -> Grey
BB-A/BB-B -> BridgeA/BridgeB, route_type=3
```

BridgeA and BridgeB are bus-bridge routes, not train lines. Keep them in the
static catalog, but exclude them from train-only assumptions.

### Normalized static-trip record

Produce one record per `(service_date, trip_id)` containing at least:

```text
service_date
trip_id
route_id
line
direction
direction_id
ordered_platform_stops
ordered_passenger_stations
terminal_station
scheduled_origin_departure
scheduled_stop_times
is_short_turn
```

Validate independently of realtime:

- stop sequences are unique and increasing;
- scheduled times are non-decreasing in service-time seconds;
- every stop ID resolves to a known station or is reported as unknown;
- route direction agrees with the route short name;
- terminal is the final published passenger station;
- Pittsburg, Pittsburg Center, and Antioch are represented distinctly;
- Yellow trips ending at Pittsburg are not extended to Pittsburg Center or
  Antioch by inference.

The checked-in static data had 0 impossible stop sequences and 0 non-monotonic
scheduled trips. It contains 2,005 stop-time fields at or after `24:00:00`,
so after-midnight handling is not an edge case.

## Stage 3: GTFS-Realtime ingestion

Parse the raw protobuf into three separate levels:

1. feed header;
2. entity/trip-update record;
3. stop-time observation record.

Do not flatten these into only a departure list. Preserve:

```text
feed_timestamp
entity_id
trip_id
route_id
start_date
start_time
schedule_relationship
stop_id
stop_sequence, nullable
arrival.time / arrival.delay
departure.time / departure.delay
stop schedule relationship
raw source path
```

Important observed behavior:

- All 483 captured trip updates lacked `route_id`; route inference must not
  depend on that field.
- 75 updates had trip IDs absent from static GTFS.
- There was 1 explicit `CANCELED` trip update.
- There were 4 duplicate trip IDs within individual feeds.
- 14 origin predictions were already stale relative to the feed timestamp.
- 407 mapped updates ended before the static terminal, but that is not proof of
  a static short turn because stop lists are commonly partial.

### Exact association first

The first association key must be:

```text
(trip_id, service_date)
```

If it maps to static GTFS, inherit the static line, direction, station pattern,
and published terminal. Apply realtime event times, delays, and explicit
status relationships on top of that pattern.

Do not require realtime `route_id` when the exact trip ID maps successfully.

### Unknown trip association

If `trip_id` does not map, retain the update as `realtime_only` and expose it
only through a confidence-marked association process. The audit emits one row
in `gtfsrt_associations.csv` for every update, including status, confidence,
method, evidence, candidate IDs, and rejected candidates. No heuristic
association is promoted to exact identity. A possible fallback score can use:

```text
same service date, if supplied
same candidate line/color
same ordered passenger stations, where enough are present
same direction
same platform IDs
origin/event time within a configured tolerance
same destination/terminal semantics
```

Recommended result fields:

```text
association_status = exact | heuristic | unknown | rejected
association_confidence = high | medium | low
association_method
association_evidence
static_identity_status = exact | no_static_counterpart
candidate_trip_ids / candidate_entity_ids
rejected_candidate_ids
```

A heuristic must never silently become an exact passenger trip identity.

The raw entity stream remains lossless. `gtfsrt_projected_entities.csv` is a
consumer projection with exactly one row per `(capture_id, trip_id)` group;
`gtfsrt_duplicate_projection.csv` records every selection and rejection. The
projection prefers an explicit cancellation, then the newest feed timestamp,
then stable source/entity ordering.

### Missing stop sequences and partial lists

When `stop_sequence` is absent:

- retain the protobuf order as `feed_observation_order`;
- resolve station identity from `stop_id` when possible;
- do not use array position as a GTFS sequence;
- do not fill missing stops from static GTFS and then claim the feed supplied
  them;
- do not set a new terminal from the last observed stop.

When a stop list is shorter than static GTFS, mark it as `partial_observation`.
Only a complete, ordered, explicitly identified update should be allowed to
replace the static pattern.

### Duplicate updates

Keep every raw entity. For a consumer projection, select deterministically:

1. preserve explicit cancellation over a non-canceled duplicate when the
   trip/entity identity is the same;
2. otherwise prefer the update with the newest feed timestamp;
3. if timestamps tie, use a stable source/entity ordering;
4. record the discarded entity IDs and selection reason.

Never deduplicate solely by a numeric entity ID across different captures.

## Stage 4: DMU and terminal telemetry

Numeric entity/trip IDs in the 600–799 range are a special data class, not a
normal route ID namespace. In the checked-in evidence they were concentrated
at Pittsburg Center/Antioch, had no route IDs, and did not map to static
passenger trips.

### BART-confirmed identity boundary

BART states that the BART-to-Antioch system and the BART schedule system
generate independent `trip_id` values. Therefore, a 600-range Pittsburg
Center/Antioch GTFS-RT trip ID is expected to have no corresponding GTFS trip.
The normal exact `(trip_id, service_date)` association must explicitly allow
this known `no_static_counterpart` result.

This identity limitation must not be confused with a service-topology
limitation. A DMU trip requires an electric train to continue from PITT to the
transfer platform, where passengers transfer between the electric train and the
DMU. The electric and DMU records may not be joinable by `trip_id`, but the
passenger service is operationally coupled.

For these records:

- preserve the raw GTFS-RT entity and stop observations;
- classify the record as `operational_telemetry` or
  `realtime_only_no_static_identity`, not as malformed GTFS;
- create or seek a paired-service relation with the required electric leg;
- if the electric leg is not present in this snapshot, record
  `required_counterpart_not_observed`, not `no_counterpart`;
- do not synthesize or infer a GTFS trip ID from numeric proximity, timing, or
  station sequence;
- do not use the missing GTFS match as evidence that the static schedule is
  missing a trip;
- do not depend on service-alert text to resolve the identity gap; alerts are
  human/context data here, not a machine-readable normalization input.

This BART statement supersedes any implementation assumption that every
GTFS-RT trip ID should resolve into the static GTFS catalog.

Recommended model:

```text
PassengerTripUpdate
OperationalTelemetryUpdate
RequiredTransferPair
```

`RequiredTransferPair` is a service relationship, not a shared trip identity.
It should be able to point to an observed electric record, an observed DMU
record, or one observed record plus a required-but-unobserved counterpart.

For an operational-to-electric association, require a documented evidence
bundle such as:

- same capture and close feed time;
- compatible terminal station(s), especially Pittsburg/Pittsburg Center/
  Antioch;
- compatible direction;
- compatible event-time window;
- no conflicting passenger trip already using the evidence.

The association should enrich a known passenger trip only when confidence is
high and the association is supported by the transfer topology. It must not be
represented as an exact GTFS trip join for the BART-to-Antioch 600-range IDs.
If no electric record is observed, expose the DMU observation with
`required_counterpart_not_observed`; this is a capture/feed limitation, not
evidence that an independent DMU-only passenger departure exists or that the
service is canceled.

Across consecutive captures, shared numeric IDs were inconsistent. Persistence
of an ID is therefore useful evidence but not a stable identity guarantee.

The audit's counterpart check is bounded to same-capture evidence and marks a
plausible electric movement as an observed candidate; it does not claim that
the numeric DMU ID and electric GTFS trip ID are equal. A missing candidate is
`required_counterpart_not_observed`, never an independent DMU-only trip or
cancellation.

## Stage 5: Yellow Millbrae and SFO handling

The official PDFs explicitly describe:

- `Antioch to SFO + Millbrae (Late Nights)`;
- `Millbrae (Early AM & Late Night) + SFO to Antioch`;
- separate SFO arrival and departure columns;
- late-night Millbrae continuation rows.

The static GTFS contains Yellow patterns that include both `SFIA` and `MLBR`,
including route 1/2 patterns. It also contains Red route 7/8 SFO–Millbrae
patterns. Preserve the actual static pattern rather than creating a synthetic
leg whenever realtime omits Millbrae.

Implementation rules:

- Treat `SFIA` and `MLBR` as distinct passenger stations.
- Preserve their order in the static trip.
- Keep PDF-backed late-night Yellow checks as optional regression fixtures; do
  not parse PDFs in the app or use them to override static GTFS.
- If a static Yellow trip includes MLBR but its realtime stop list ends at
  SFIA, mark `realtime_pattern_partial`; do not remove MLBR from the static
  trip.
- Only create an operational transfer/synthetic leg when the source evidence
  explicitly requires a transfer. Mark it `synthetic`, retain its source
  timing, and never present it as a GTFS trip.
- Treat SFO arrival/departure platform semantics as separate evidence when
  matching ETD rows; a single GTFS station row may not encode both events.

The PDF comparison found 2,036 Yellow comparisons. Static and PDF times agreed
for 2,035; the one captured Yellow Millbrae observation differed by 3 minutes
(GTFS static 8:58 PM versus PDF 9:01 PM). The regression policy allows up to
two mismatches per PDF when each is under five minutes, accommodating a likely
PDF-preparation typo. The observed mismatch is within that allowance and is
ignored for normalization; static GTFS remains the app-facing schedule source.

The operational question “does every late-night Yellow movement have a
realtime counterpart?” remains unresolved from the checked-in fixture set.
There is only one captured Yellow GTFS-RT stop row reaching Millbrae, so the
absence of additional rows is not negative operational evidence. A paired
late-night capture series is required to resolve that question.

## Stage 6: ETD corroboration

ETD should be a separate evidence adapter, not a replacement for GTFS identity.
Normalize each prediction as:

```text
capture_id
station
line/color
destination_label
destination_abbreviation
platform
direction
minutes
absolute_prediction_time
status = leaving | future | canceled
delay_seconds
dynamic_flag
request_time
raw_source_path
```

Matching order:

1. passenger station;
2. color/line;
3. platform or direction;
4. destination label/abbreviation;
5. absolute time within a documented tolerance.

Use one-to-one matching. The audit used a 180-second absolute-time window,
which accommodates minute rounding and small request/feed skew. Keep
`ambiguous`, `etd_only`, and `gtfsrt_only` rows rather than forcing a match.

Special ETD cases:

- `Leaving` means the prediction is effectively at request time, not a future
  numeric minute.
- `cancelflag=1` is explicit ETD cancellation evidence, but still does not
  identify a GTFS trip.
- `dynamicflag=1` and unusual destination labels may describe disruption
  service rather than the static terminal.
- A short ETD look-ahead is not evidence that later static trips are absent.

## Source-of-truth matrix

| Fact | Primary source | Fallback/corroboration | Never do |
|---|---|---|---|
| Published station order | static GTFS | none; PDF checks are test-only | infer from partial RT stop list |
| Published terminal | static GTFS | complete RT evidence | extend PITT to PCTR/ANTC automatically |
| Published service date | GTFS calendar + exceptions | none required | use capture wall-clock date alone |
| Realtime arrival/departure | GTFS-RT event time | ETD with provenance | replace with static time silently |
| Explicit cancellation | RT `CANCELED` | ETD cancel flag, if separately supported | infer cancellation from omission |
| Pittsburg Center/Antioch 600-range update | separate operational telemetry layer plus required electric-transfer relation | separately documented operational association; mark counterpart unobserved when absent from the capture | join to GTFS by trip ID, treat DMU as independent service, or depend on alert text |
| Other unknown operational train | separate telemetry layer | high-confidence heuristic association | invent a passenger trip ID |
| Passenger-facing corroboration | ETD | static schedule | use ETD as universal ground truth |
| Late-night Yellow Millbrae schedule | static GTFS pattern | RT timing overlay | synthesize a shuttle when static MLBR exists |

## Consumer projections

Different consumers should not receive the same flattened record.

### Schedule and route planning

Use static trips after service-date filtering. Add realtime timing only when the
trip association is exact or explicitly high-confidence. Preserve planned
station order even when a realtime update is partial.

### Departure board

Use realtime event times for exact trips, include an explicit status, and expose
provenance/confidence for heuristic or ETD-corroborated rows. Keep static-only
departures as `schedule_only` or `unknown`, not canceled.

### Terminal/DMU display

Consume the operational telemetry layer separately. A telemetry row may explain
Pittsburg/Pittsburg Center/Antioch movement without being safe to show as an
independent passenger departure.

### Diagnostics

Show raw IDs, source timestamps, matching method, deltas, and capture flags. A
diagnostic view should make it possible to explain every user-visible row.

## Required regression fixtures

At minimum, retain tests for:

- `24:xx:xx` service times and next-day absolute timestamps;
- calendar-date additions and removals;
- route direction and BridgeA/BridgeB exclusion from train logic;
- platform stop IDs resolving to parent stations;
- missing route IDs;
- missing stop sequences;
- partial stop lists that stop before a static terminal;
- explicit `CANCELED` versus omitted static trips;
- duplicate trip IDs in one feed;
- stale origin predictions;
- numeric 600–799 DMU records with and without an electric candidate;
- DMU records whose required electric counterpart is absent from the snapshot;
- paired DMU/electric transfer observations north of PITT;
- Pittsburg, Pittsburg Center, and Antioch evidence;
- Yellow static trips reaching SFO and Millbrae;
- late-night Yellow static trips reaching MLBR, including after-midnight times;
- distinct SFIA arrival/departure and MLBR station identities;
- ETD `Leaving`, cancellation, dynamic, rounded-minute, and destination-label
  cases;
- ETD/GTFS-RT capture-time skew;
- one-to-one ETD matching and ambiguous candidates.

## Recommended implementation sequence

1. Build immutable provenance and time utilities.
2. Build and test the static catalog independently.
3. Build raw GTFS-RT feed/entity/stop normalizers.
4. Add exact trip association and conservative status projection.
5. Add partial-list, duplicate, stale-time, and terminal diagnostics.
6. Add the separate DMU/operational telemetry model.
7. Add optional PDF-backed Yellow/SFO/Millbrae regression fixtures, allowing
   up to two per-PDF mismatches under five minutes.
8. Add ETD corroboration as an optional, confidence-marked adapter.
9. Only then build consumer-specific departure and routing projections.

The key architectural constraint is that normalization should make uncertainty
visible. The reliable correction is not one universal “best” feed; it is a
layered model where static schedule structure, realtime operations, ETD
passenger evidence, and specialized telemetry retain distinct authority and
provenance.
